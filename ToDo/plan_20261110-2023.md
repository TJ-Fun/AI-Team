# PM/agent on-demand project context — plan

Status: **Batch 4 complete** (v0.75). Next: Batch 5 — frontend buttons + roadmap doc viewer.

## Goal

Agents (PM/PO chat + all work roles) stop receiving full project context on every call. Instead they get:

1. A compact **document map** (~200–400 tokens): doc slug, title, one-line description, size, and whether it is auto-injected or on-request.
2. **Role minimums**: a per-role set of docs always injected (auto).
3. An **`info_requests` mechanism**: the agent may request docs by slug in its reply envelope; the app loads them and continues the conversation with a bounded follow-up call (max 2 rounds, cached per attempt, unknown slugs ignored).
4. Two new PM/PO task types with approval-gated writes: **Update project documentation** and **Update roadmap**.

Provider/model agnostic — works with Gemini and all OpenAI-compatible providers because it is prompt-in/prompt-out, no function-calling API.

## Document registry (new/changed)

Existing context docs (`PROJECT_CONTEXT_FILES`): `project_brief`, `technical_overview`, `decisions`, `outcomes`.

New roadmap docs (stored alongside context docs, same history/versioning):

- `master_plan` — big plan / roadmap overview.
- `phase_N` — per-phase plan docs (`phase_1` … `phase_9`), created on demand.
- `active_phase` — integer pointer stored on the project record (not a doc).

## Role → auto / on-request matrix (proposal)

| Doc | PM/PO | Frontend | Backend | QA | UI designer | Documentation |
|---|---|---|---|---|---|---|
| project_brief | auto | on-req | on-req | on-req | auto | auto |
| technical_overview | on-req | auto | auto | auto | on-req | auto |
| decisions | on-req | on-req | on-req | on-req | auto | on-req |
| outcomes | on-req | on-req | on-req | auto | auto | auto |
| master_plan | auto | on-req | on-req | on-req | on-req | on-req |
| phase_N | on-req | on-req | on-req | on-req | on-req | on-req |

Always auto (unchanged, not docs): project identity/repo/modules, live board + recent replies for PM/PO only, task request itself.

Rationale: PM plans → needs brief + roadmap; workers need tech stack to build; QA needs outcomes + tech overview to verify; UI designer keeps today's brief/decisions/outcomes; Documentation needs structure + outcomes.

## Risks / notes

- Small models may under-request → mitigated by doc-map descriptions, strict prompt rule, activity-log visibility of requests.
- Token win: ~4–8k → ~0.5–1k tokens baseline per call; docs only cost when requested.
- `active_phase` gives PM a "where are we" pointer without injecting all phase plans.
